# WorkBuddy 积分消耗统计

回答一个问题：**积分到底花在哪儿了？**

产物是一段可嵌进周报的 Markdown，或一份独立 HTML 报告。数字全部来自本机落盘的记录，没有估算成分。

## 数据从哪来

| 来源 | 位置 | 作用 | 局限 |
|---|---|---|---|
| `session_usage` 表 | `~/.workbuddy/workbuddy.db` | **总量最全**：每个会话的 `credit_json` = {请求ID: 积分} | 按会话最后活动时间归日，跨零点长会话整体落到结束日 |
| 运行日志 | `~/.workbuddy/logs/YYYY-MM-DD/*.log` + `*.old.log` | 拆**模型 / token / 场景 / 时段**，逐条调用级 | 会轮转，只覆盖最近数日，覆盖率要在报告里标出来 |
| `sessions` 表 | 同上 db | 会话标题、项目目录、所用模型 | 标题由模型自动生成，偶尔很笼统 |

两者交叉校验过：日志覆盖的日期里，日志积分约为库内记录的 78%—98%（差额是轮转丢掉的旧行）。所以**总额永远取库，结构才用日志**。

## 怎么跑

```bash
S=~/.workbuddy/skills/workbuddy-credit-report/scripts/credit_report.py

python3 $S                          # 默认：近 7 天 + 近 30 天，控制台表格 + 观察 + 建议
python3 $S --detail                 # 追加模型/token/时段明细（读日志，约 2 秒）
python3 $S --automations            # 追加「定时任务」拆分 + 按排期推算的稳态周消耗
python3 $S --md                     # 输出 Markdown 片段（周报直接用这个）
python3 $S --json                   # 完整结构化数据，供二次加工
python3 $S --days 14                # 只看最近 14 天
python3 $S --from 2026-10-27 --to 2026-11-02 --md   # 指定区间（周报用这个口径）
python3 $S --html 报告.html          # 出独立单页 HTML
```

写周报时用 `--from/--to` 锁死「本周一 ~ 运行时刻」，比滚动的 `--days 7` 更贴合周报语义。

## 定时任务单独算（`--automations`）

问题「定时任务每天/每周花多少」不能拿总会话去猜，必须只挑自动化产生的那部分。

关联方式：`automation_runs.metadata_json` 里的 `sessionId` → `session_usage.session_id`。一次运行一个会话，归因干净，不会和手动会话混。

输出两套数，别混为一谈：

| 口径 | 含义 | 用途 |
|---|---|---|
| **实测**（区间） | 该区间内实际跑掉的积分 ÷ 天数 | 回顾「上个月定时任务花了多少」 |
| **稳态**（按排期） | Σ（该自动化历史单次成本中位数 × RRULE 折算的每周次数），仅计 `status=ACTIVE` 且未删除的 | 回答「以后每周会花多少」——新加的自动化靠这个才准 |

稳态用**中位数**而不是均值，避免一次异常跑崩把预测带偏。RRULE 折算只处理 HOURLY / DAILY / WEEKLY / MONTHLY / YEARLY 加 `INTERVAL`，其它频率返回 0 并在结果里体现为「未计入」。

实测和稳态出现明显差距是正常的，三个常见原因：新排期的自动化还没跑满一个周期；有 `runKind=missed` 的补跑；某自动化已停用（PAUSED / 已删）但历史还在。

零消耗运行要单独看一眼：`has_session=false` 说明那次运行根本没建会话（启动即失败），不是「白嫖成功」。

## 口径（写进报告，别省）

- **积分**：`credit_json` 求和，WorkBuddy 积分单位。
- **对话轮次**：根请求数，**不等于消息条数**。一轮对话里可能几十次模型调用。
- **日均**：同时给「自然日」和「活跃日」两个口径，静默日会把自然日均值拉低。
- **集中度**：Top1/Top3/Top5 会话占总额比例，判断预算是不是被少数重活吃掉。
- **单笔最大**：占本期 ≥15% 就点名写出来，带标题、日期、模型、轮次。

## 怎么读这份数据

四条常看的信号：

1. **集中度 > 50%** → 预算是被几次「一键大活」吃掉的，不是被日常问答。日常不用省，重活才要管。
2. **峰值日 / 中位日 > 5 倍** → 脉冲式消耗。这种节奏下「日均」没意义，看单次成本。
3. **单会话中位数只有个位数** → 绝大多数会话很便宜，焦虑点放错地方了。
4. **日志覆盖率低** → 只说明日志轮转了，不是漏账；别据此推断「系统少算了」。

## 报告里怎么写

`--md` 已经生成好表格、观察、建议三段。直接用，但**至少补一句你自己的判断**——落到「这周该不该收着点、哪类活该拆」上，不要复述数字。

判断要具体，比如：

- 「这周的 460 分有一次飞行游戏改动独占，属于典型的一次性重活，下不为例不算问题。」
- 「连续三周 Top1 都是同一个项目，说明它是真正的吞金口，值得单独优化上下文。」

不要写的：涨粉式鼓励、无意义的「继续保持」、把数字换个说法再说一遍。

## 已知坑

- **别拿 `used`/`size` 当 token 数**：那是上下文窗口占用量，不是计费 token。
- **`credit_json` 的 key 是请求 ID，不是消息 ID**：所以轮次会明显小于日志里的调用次数，两者不能互相校验。
- **日志里每条 credit 会重复三次**（`modelUsage` / `rawUsage` / `stream`），必须按 `messageId` 去重，否则数字翻三倍。
- **日志时间戳格式是 `[11/2/2026, 5:18:05 PM.577]`**，AM/PM 在毫秒前面，正则容易写错导致解析出 0 条。
- **`*.old.log` 没有日期目录**，只能靠行内时间戳定位，别忘了扫。

## 边界

- 只读本机文件。不登录网页端、不抓 growth-center、不读 Cookie。
- 网页端账户余额和这里的「消耗」是两个概念：这里算的是**已消耗**，不推算余额，除非用户主动给了余额数字。
- 报告里不要出现任何凭证、token、邮箱。
