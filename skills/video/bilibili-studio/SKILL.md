# B 站创作闭环

> **⚠️ 本技能的 `biliup` 上传通道已于 2026-10 失效**（登录接口废弃、`preupload` 恒 `-400`）。
> 要投稿请走 `bilibili-explainer/scripts/web_upload.py`（真实浏览器 + 已有 cookie）。
> 本技能保留价值在**数据侧**：抓数据、复盘、更新策略库——这部分接口仍然正常。

> **投稿素材是科普短片时，先走 `bilibili-explainer`。** 那个技能负责「事实核查 → 旁白 → 配音 → 画面 → 渲染 →
> 封面」，工程落在 `~/BilibiliVideos/<slug>/`。本技能保留为数据侧：抓数据、复盘、更新策略库。

一个把「投稿 → 复盘 → 学习」串成闭环的技能。核心不是自动上传，而是**每投一条视频都在验证一个假设**，
让第 10 条视频比第 1 条更有可能跑出来。

## 能做什么 / 不能做什么

| 能做 | 不能做 |
|---|---|
| 上传视频、封面、标题、简介、标签、分区、定时发布 | 代替人做实名认证 |
| 抓完播率/3秒退出率/互动率/播转粉率并生成诊断 | 抓观众留存曲线的逐秒数据（只在创作中心网页有） |
| 算出账号基线，判断新视频是否跑赢自己 | 保证审核通过（B 站人工+机审，不受控） |
| 把结论写进策略库并在下次投稿时应用 | 刷量、互赞、绕过风控（**拒绝执行**） |

## 硬前提（缺一不可）

1. **登录凭证**：`data/cookies.json` 里的 SESSDATA + bili_jct。首次需扫码，之后可复用至过期。
2. **视频文件**：本地路径，B 站网页端单文件上限 8GB。
3. **Python 环境**：`python3`（零第三方依赖，只用了标准库）。
4. **biliup 二进制**：`bin/biliup`，已内置（v0.2.4）。若失效可从 `github.com/biliup/biliup-rs/releases` 重下 `x86_64-macos` 包解压覆盖。

> **「完全自主」的真实边界**：登录要人扫一次码，发布前要人点一次确认。
> 这两处不设自动化，因为一次误发不可撤回，一次凭证泄露不可挽回。其余全流程可无人干预。

## 阶段 0 · 环境自检（每次会话开始先跑）

```bash
PY=python3
S=~/.workbuddy/skills/bilibili-studio/scripts/bili.py
$PY $S auth-check
```

- 返回 `ok: true` → 直接进入流程，顺带记下粉丝数。
- 返回 `need_login: true` → 走登录：
  ```bash
  $PY $S auth-login      # 拉起终端二维码，让用户用 B 站 App 扫
  ```
  扫码必须在**用户本人在场**时做。如果用户不方便扫码，让他从浏览器 F12 → Application → Cookies
  复制 `SESSDATA`、`bili_jct`、`buvid3`，然后：
  ```bash
  $PY $S auth-import --cookie "SESSDATA=xxx; bili_jct=yyy; buvid3=zzz"
  ```
- 凭证有效期通常数月，过期后 API 返回 `-101`，重跑 auth-login 即可。

## 阶段 1 · 投稿

### 1.1 先读策略库

**必读** `references/playbook.md`。里面的每条策略带着状态（✅已验证 / ⚠️假设 / ❌已证伪）。
本次投稿的标题、封面、时长、分区、发布时段，**优先采用已标记 ✅ 的策略**；
如果还没有任何 ✅ 条目（新号常态），就挑一条 ⚠️ 假设来验证。

### 1.2 设计本次投稿

按这个顺序准备四样东西：

**① 标题**（≤80 字）
- 从 `references/playbook.md` 的标题策略出发，产出 3 个候选，说清每个候选在验证什么。
- 标题必须和内容一致。标题党会让你在「高播放 + 低完播」的死局里，短期好看长期掉权重。

**② 封面**（≤5MB，建议 16:9，1146×717 以上）
- 可以用 ImageGen 生成，也可以从视频里截一帧。
- 封面上文字不超过 2 行、主视觉占画面 60% 以上。

**③ 分区**（tid）
- 查 `references/tid.md`。**2026-10 起二级分区已取消**，网页上只能选一级：科普/原理 → **知识（36）**，
  动手做 → 手工，软件/工具 → 科技数码，游戏 → 游戏（4）。别再照旧表找「201 科学科普」，界面上没有。

**④ 标签**（≤10 个，逗号分隔）
- 结构：2 个大词（覆盖面）+ 4~6 个精准词（让算法找准人）+ 1~2 个系列词。
- 例：`纸飞机,空气动力学,科学实验,物理,手工DIY,中学生` —— 大词带流量，精准词定受众。

### 1.3 先 dry-run，再发布

**永远先跑不带 `--yes` 的版本**，把将要提交的内容完整给用户看：

```bash
$PY $S upload \
  --video "/path/to/video.mp4" \
  --title "标题" \
  --desc "简介" \
  --tags "标签1,标签2,标签3" \
  --tid 201 \
  --cover "/path/to/cover.jpg" \
  --hypothesis "验证：开场给结论能否提升完播率"
```

确认无误后加 `--yes` 才会真正上传。**这一步必须等用户明确说「发」**，
不能因为用户前面说过「帮我发」就跳过确认——那是授权整个流程，不是授权这一条。

### 1.4 上传后

- 上传成功会打印台账记录。biliup 输出的 BV 号要手动补进台账：
  ```bash
  $PY $S ledger add --json '{"bvid":"BV1xxxx","title":"...","status":"submitted"}'
  ```
- 提醒用户：B 站审核通常数小时内，过审后数据次日中午才开始有意义。

## 阶段 2 · 复盘

### 2.1 时机

| 距发布 | 动作 |
|---|---|
| < 24 小时 | 数据未刷新，**不要复盘**，只告知用户等 |
| 24~48 小时 | 主复盘窗口，跑完整流程 |
| 7 天 | 看长尾，判断能否做系列 |
| 30 天 | 纳入基线样本 |

用户催着当天复盘时，直接说明：B 站统计次日中午才刷新，现在看到的是半成品数据，
拿它下结论会误导下一次投稿。

### 2.2 拉数据

```bash
$PY $S review --size 10        # JSON，适合你直接读
$PY $S report --size 10        # 生成 Markdown 报告 + 数据快照
```

`review` 返回的每条视频已带：
- `pct` — 换算成百分数的五维指标
- `diagnosis` — 结构化诊断信号（level: good/warn/bad + finding + cause）
- `vs_baseline` — 相对账号中位数的倍数
- `baseline` — 账号基线

### 2.3 判读

对照 `references/review-metrics.md` 的组合诊断矩阵。**不要只看播放量**，
播放低但完播高 = 内容和分发脱节；播放高但完播低 = 标题党。

回答用户时要说清三层：
1. **现象**：哪个指标异常（给数字）
2. **归因**：最可能的原因（给依据，说清是推断不是定论）
3. **动作**：下一条视频具体改什么（要可执行，不要「多优化封面」这种废话）

### 2.4 别下的结论

- 样本 < 5 条时，任何「规律」都可能是巧合，只能说是倾向。
- 单条视频的爆或扑，大概率是分发运气，不能直接归因到某个技巧。
- 不要用「播放/粉丝数」当指标，没有意义。

## 阶段 3 · 学习（这是技能真正的价值）

复盘完必须**改 playbook**，否则下次投稿还是凭感觉。

### 3.1 更新什么

打开 `references/playbook.md`，按证据更新：

| 情况 | 怎么改 |
|---|---|
| 本次视频验证了某假设，且方向一致 | 样本数 +1；累计到 3 且同向 → `⚠️假设` 改 `✅已验证（n=3）` |
| 结果与假设相反 | 样本数 +1；标记 `❌已证伪（n=N）`，写清反例数据 |
| 结果混杂/受干扰 | 样本数 +1，保持 `⚠️假设`，注明干扰因素（如发布时间异常） |

同时在「假设验证记录」表追加一行：日期、BVID、验证的假设、结果、结论。

### 3.2 更新基线

`report` 已经算出了新的中位数，把它抄进 playbook 的「基线」表，样本数更新为实际条数。

### 3.3 定下一次的验证目标

在 playbook 末尾「本次投稿要验证什么」写一句：
> 一次只动一个变量。同时改标题、封面和时长，数据涨了也不知道是谁的功劳。

### 3.4 反馈给用户

用两三句话说清：这次学到什么、下次试什么、还差多少样本能定论。
不要说「已更新策略库」就完事——用户要的是判断，不是日志。

## 安全红线（无条件遵守）

1. **发布必须二次确认。** 任何 `--yes` 之前都要让用户看到完整投稿计划并明确同意。
2. **不刷量、不互赞互粉、不用脚本制造虚假互动。** 被识别后掉权重比没流量更严重。
3. **不改已有稿件的内容去「洗数据」。** 改标题封面会让历史数据失去可比性，破坏复盘样本。
4. **凭证只存在本地 `data/cookies.json`（权限 600）**，绝不写进对话、日志、公开文件。
5. **不代填转载内容而不标来源。** `--copyright 2` 时必须填 `--source`，这是版权底线。
6. 遇 `-352 / -412 / -509` 风控码，**立即停止，不要重试**，告知用户稍后再试。

## 常见错误对照

| 现象 | 原因 | 处理 |
|---|---|---|
| `-101 账号未登录` | 凭证缺失/过期 | `auth-login` 重扫 |
| `-400 请求错误`，秒回且无任何上传进度 | **biliup 0.2.4 的 `preupload` 已与 B 站接口脱节**，与视频、分区、线路都无关 | 别修了。改用 `bilibili-explainer/scripts/web_upload.py` 走网页投稿 |
| 扫码登录一直拿不到 token | `biliup login` 调的是已废弃的 `passport-tv-login/qrcode` | 同上，走网页投稿 |
| `-352 风控校验失败` | 请求过频或环境异常 | 停 30 分钟以上，别重试 |
| 上传中断/卡住 | 线路问题 | 加 `--line bda2` 或 `--line qn` 换线路重试 |
| `投稿失败，分区错误` | tid 不对 | 查 `references/tid.md` 重选 |
| 封面报错 | 超过 5MB 或尺寸不符 | 压到 5MB 内，16:9 |
| 稿件一直「审核中」 | 正常排队或触发机审 | 等，超过 24 小时去创作中心看原因 |
